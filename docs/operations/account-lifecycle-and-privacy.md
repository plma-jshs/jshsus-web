# 계정 생명주기와 개인정보 파기 운영안

작성 기준일: 2026-07-31

## 결론

- 학생 졸업 처리는 `users.status = 'graduated'`와 해당 학년도
  `student_enrollments.status = 'graduated'`만 변경한다. `students`, 상벌점,
  탐구활동서, 게시글·댓글은 삭제하지 않으므로 현재 구현에서 기록이 유실되지 않는다.
- 학생 전학·자퇴도 `student_enrollments.status`를 `transferred` 또는 `withdrawn`으로
  바꾸고 로그인 계정을 비활성화하는 방식이어야 한다. `students`나 `users`를 바로
  물리 삭제하면 여러 외래 키 때문에 실패하거나, 참조 규칙을 잘못 바꿀 경우 기록이
  연쇄 삭제될 위험이 있다.
- 교직원 계정은 별도의 재직 상태가 없다. 전근 시 `users.status`만
  `restricted`/`deleted`로 바꾸는 임시 처리 대신, `staff_profiles`에 재직 상태와
  종료일을 추가하는 후속 마이그레이션이 필요하다.
- 계정 이용 종료와 개인정보 파기는 같은 작업이 아니다. 먼저 로그인을 차단하고,
  정해진 보존기간이 끝난 항목을 승인된 파기 배치가 비식별화·영구 삭제해야 한다.

## 현재 참조 무결성 점검

| 기록                           | 식별자 참조                               | 졸업/전근 상태 변경 | 사용자를 물리 삭제할 때                         |
| ------------------------------ | ----------------------------------------- | ------------------- | ----------------------------------------------- |
| 상벌점 `point_records`         | 학생, 처리 교사, 사유                     | 유지됨              | 학생/교사 외래 키가 삭제를 막음                 |
| 탐구활동서 `activity_requests` | 대표 학생, 참여 학생, 작성·지도·검토 교사 | 유지됨              | 학생/교사 외래 키가 삭제를 막음                 |
| 게시글·댓글                    | 작성 사용자 + 작성자명 스냅샷             | 유지됨              | 작성자 외래 키가 삭제를 막음                    |
| 감사챌린지 `thanks_messages`   | 학번 문자열                               | 유지됨              | 사용자 삭제와 무관하지만 학번은 개인정보로 남음 |
| 좋아요                         | 사용자                                    | 유지됨              | 사용자 삭제 시 의도적으로 연쇄 삭제됨           |

현재 외래 키는 기록 유실을 막는 쪽으로 동작하지만, 물리 삭제를 직접 실행할 수 있는
완성된 탈퇴 워크플로는 없다. 관리자 명단 반영은 학생 졸업만 안전하게 상태 전환한다.

## 법 기준을 운영 규칙으로 옮기기

개인정보 보호법 제16조의 최소 수집 원칙과 제21조의 목적 달성·보유기간 경과 후
지체 없는 파기 원칙을 기준으로 한다. 다른 법령 때문에 보존해야 할 때에는 운영 DB의
일반 개인정보와 분리해 보관하고, 전자 파일은 복구할 수 없는 방식으로 삭제한다.

- 개인정보 보호법 제16조:
  <https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335671>
- 개인정보 보호법 제21조:
  <https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900078981>
- 개인정보 보호법 시행령 제16조:
  <https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0016&lsiSeq=286175&urlMode=lsScJoRltInfoR>
- 개인정보보호위원회 파기 절차 예시:
  <https://www.pipc.go.kr/np/default/contents.do?cIdx=223&isBlank=true>

학교가 적용해야 할 정확한 보존기간은 개인정보처리방침, 학교 기록물 분류표와
관계 법령을 개인정보 보호책임자가 확인해 확정한다. 아래 값은 기간을 임의로
확정하지 않고 안전한 실행 순서를 정의한 것이다.

## 졸업·전학·자퇴·전근 처리

1. 즉시 로그인 차단
   - `users.status`를 `graduated`, `restricted` 또는 `deleted`로 전환한다.
   - 세션, 활성화 코드, 비밀번호 재설정 코드와 Cognito 세션을 폐기한다.
   - Cognito 계정은 비활성화한 뒤 학교 보존정책에 따른 유예기간 후 삭제한다.
2. 연락처와 선택 프로필 최소화
   - 서비스 연락 목적이 끝난 `email`, `phone`, `nickname`, `gender`, 프로필 파일과
     알림 수신 정보를 삭제한다.
   - 비밀번호 해시와 로컬 인증 계정은 즉시 제거한다.
3. 학교 기록 보존
   - 상벌점·탐구활동 기록은 학생 행정 기록의 확정 보존기간까지 접근권한을 제한해
     유지한다.
   - 게시글·댓글은 처리방침상 보존 근거가 없다면 작성자 연결과 작성자명 스냅샷을
     `탈퇴한 사용자`로 비식별화한다. 본문에 작성자가 직접 쓴 개인정보는 별도
     신고·검토 대상으로 처리한다.
   - 감사챌린지는 학번을 내부 무작위 식별자로 치환하거나, 목적 달성 시 메시지와
     학번 연결을 파기한다.
4. 보존기간 종료 후 파기
   - 대상 조회 결과와 건수를 먼저 출력하는 `--dry-run`을 실행한다.
   - 개인정보 보호책임자 승인 번호, 대상 범위, 실행자, 실행시각과 결과 건수만
     감사 로그에 남긴다. 삭제 대상 원문은 로그에 남기지 않는다.
   - 백업에도 같은 만료 정책을 적용하고, 만료 백업은 복구 불가능하게 삭제한다.

## 구현 순서

1. `staff_profiles`에 `active/transferred/retired` 상태와 `ended_at`을 추가한다.
2. `privacy_retention_policies`, `privacy_erasure_jobs` 테이블로 승인·드라이런·실행
   상태를 기록한다.
3. `users` 삭제 전에 모든 콘텐츠 작성자 참조를 `NULL`로 바꾸고 표시 이름을
   비식별화하는 트랜잭션 서비스를 만든다.
4. 학생 행정 기록은 별도 보관 영역으로 이동하고 운영 서비스 계정에서는 조회하지
   못하게 한다.
5. 정기 배치를 월 1회 실행하되, 법적 보존 중·분쟁 중·감사 중인 레코드는
   legal hold로 제외한다.

직접 SQL로 `users` 또는 `students`를 삭제하는 운영은 금지한다. 완성된 파기 서비스가
도입되기 전에는 상태 전환과 로그인 차단만 수행한다.
