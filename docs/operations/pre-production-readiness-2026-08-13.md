# v26 공개 전 준비 상태와 운영 체크리스트

작성일: 2026-08-14  
대상: `v26` 웹, 관리자, API 및 전용 데이터베이스

이 문서는 코드와 인프라를 점검한 결과를 기록한 운영 기준이다. 문서에 적힌
명령이나 변경 후보는 자동 실행을 뜻하지 않는다. 운영 데이터 변경, DNS 변경,
배포, 재시작은 반드시 별도의 승인과 작업 창을 확보한 뒤 수행한다.

## 1. 범위와 절대 금지 사항

### 이번 점검 범위

- 모노레포 구조, 빌드, 컨테이너, CI/CD 설정
- v26 스키마, 마이그레이션, 인덱스 후보, 데이터 정합성
- 인증과 권한 경계, 계정 활성화 절차
- 백업, 복구, 로그, 모니터링, 디스크 관리
- v26 전용 배포 디렉터리와 공유 인프라 의존성
- SEO, favicon, OG 메타데이터, 정적 자산과 번들 크기

### 절대 변경하지 않는 범위

- 기존 `jshsus.kr`, `iam.jshsus.kr`, `points.jshsus.kr` 및 관련 서비스
- 기존 PHP 서비스의 파일, 프로세스, 웹 서버 설정과 원본 데이터베이스
- 공유 프록시, 공유 DNS, 공유 방화벽을 통한 기존 서비스의 트래픽 경로
- 운영 데이터의 삭제, 덮어쓰기, 마이그레이션 재실행

기존 서비스는 v26 공개와 승격이 완료되고 별도의 폐기 승인을 받기 전까지
**병행 운영 대상**이다. 기존 서비스의 디렉터리·프로세스·원본 DB·프록시 설정은
v26 변경으로 재시작되거나 재적용되어서는 안 된다. 두 서비스가 동시에 쓰기를
받는다면 원장 DB와 동기화 계약을 먼저 승인하고, 승인 전에는 양방향 동기화를
추가하지 않는다.

## 2. 현재 판정

**판정: NO-GO**

현재 코드는 개선 중이지만, 아래 P0 항목이 모두 닫히기 전에는 학생에게 URL과
인증코드를 공개하지 않는다. 단순히 빌드와 헬스체크가 성공했다는 이유만으로
GO로 전환하지 않는다.

GO 전환 조건:

1. P0 보안·계정 항목이 해결되고 회귀 테스트가 통과한다.
2. 운영 데이터 변경 전 백업과 격리 복원 검증이 완료된다.
3. 테스트 계정·샘플 데이터의 공개 정책이 확정된다.
4. v26 전용 경로만 대상으로 한 배포와 롤백 리허설이 성공한다.
5. 공개 후 담당자, 모니터링 채널, 장애 대응 연락 경로가 지정된다.

### 로컬 후보 코드에 반영된 항목

아래 항목은 로컬 작업 트리와 테스트에서만 확인되었다. 아직 커밋·배포·운영
데이터 반영을 하지 않았으므로 운영 완료로 간주하지 않는다.

- 계정 활성화 코드에 30일 기본 만료 시각과 활성 학년도 결속 추가
- 학생과 교직원 인증코드에 같은 학년도 경계 적용
- 비밀번호 찾기에서 Cognito가 확인한 검증 연락처만 사용하고 계정 존재 여부를
  응답 차이로 노출하지 않도록 보완
- 사용 완료된 계정의 활성화 코드 강제 재발급 차단
- 장치 remote API 기본 비활성화 및 별도 bearer token 적용
- 사용자별 업로드 총량과 동시 요청 우회 방지 적용
- 공개 상세 조회수 쓰기 Redis 중복 제거·전역 예산 적용
- 게시물 파일의 권한 검사와 짧은 수명의 presigned URL 적용
- 상태 변경 로그아웃을 POST로 전환하고 GET은 무해한 이동만 허용
- 청원 참여 또는 답변 이후 작성자 임의 삭제 차단
- 과구리 웹에서만 GA4 페이지뷰를 수집하고 관리자 GA는 제거
- Docker build context의 환경파일·키·덤프 유입 차단
- 정적 메타데이터, robots 정책, 캐시 정책, 이미지 최적화 반영

## 3. 출시 차단 항목(P0)

### 3.1 계정 활성화와 권한

- 기존 미사용 인증코드 일부에는 만료 시각과 학년도 결속이 없다. 신규 코드는
  만료 정책을 적용하되, 기존 코드는 공개 전에 백업 후 **재발급·교체**해야 한다.
- 사용이 끝난 활성화 코드는 `force` 옵션으로도 재발급할 수 없어야 한다. 그렇지
  않으면 사용자 관리 권한만 가진 계정이 고권한 계정의 인증 수단과 비밀번호를
  재설정할 수 있다.
- 레거시 역할명과 환경변수 기반 관리자 승격은 정식 IAM 역할 부여를 확인한 뒤
  제거한다. 전환 검증 없이 먼저 제거하면 운영자 접근이 끊길 수 있다.
- 배포 전에 학생, 교직원, 학생관리부장, 시스템 관리자 각각의 최소 권한 계정으로
  접근 허용·거부 시나리오를 테스트한다.

### 3.2 공개되지 않은 장치 API

장치 상태 조회·갱신 경로는 장치 자격 증명 없이 공개되어서는 안 된다. 공개 전
둘 중 하나를 선택한다.

1. 기능이 아직 사용되지 않으면 환경설정으로 완전히 비활성화한다.
2. 사용한다면 장치별 자격 증명, 요청 인증, 재전송 방지, 속도 제한과 감사 로그를
   적용한다.

공용 웹 사용자 세션을 장치 인증 수단으로 재사용하지 않는다.

### 3.3 레거시 시드 데이터와 개인정보

레거시 콘텐츠 시드에는 실명, 연락처 형식 문자열, 과거 작성자 정보가 포함될 수
있다. 이 파일을 매 배포 때 재적재하는 구조는 중단하고 다음 절차로 분리한다.

1. 공개 승인된 필드와 게시물만 추출한다.
2. 개인정보와 불필요한 메타데이터를 삭제 또는 가명 처리한다.
3. 결과물을 검토 가능한 일회성 import로 만든다.
4. import 후 일반 bootstrap 경로에서 레거시 시드를 제거한다.

원본 덤프나 비식별화 전 콘텐츠를 공개 저장소에 추가하지 않는다.

### 3.4 배포 신뢰성과 테스트 데이터

- Cloudflare 차단 응답을 정상 헬스체크로 취급하는 예외는 제거한다. API는 예상한
  상태 코드와 응답 본문을 모두 만족해야 성공이다.
- 공개 README, 시드, 자동 bootstrap에 고정된 테스트 비밀번호가 남지 않도록 한다.
  테스트 계정이 필요하면 staging 전용 플래그와 별도 비밀값으로 생성하고,
  production에서는 생성되지 않음을 테스트한다.
- `main` 직접 push가 자동 배포를 시작하는 구조라면 branch protection, 필수 CI,
  배포 environment 승인 중 최소 하나 이상의 변경 통제를 적용한다.

## 4. 높은 우선순위(P1)

- 사용자별 누적 업로드 제한은 일반 사용자와 관리자 모두 기본 1GB로 맞췄다.
  운영 환경의 실제 값은 배포 환경 변수에서 최종 확인한다.
- 공개 상세 조회는 IP를 식별·제한하지 않는다. 비로그인 조회는 제한 없이 기록하고,
  로그인 사용자는 계정 단위 중복 기록 방지만 적용한다. Redis 장애 시 본문 조회는
  계속 허용하되 조회수 쓰기는 건너뛰는지 staging에서 확인한다.
- 로그아웃의 상태 변경은 POST로 전환되었다. SSO와 각 surface에서 회귀 테스트한다.
- 데이터베이스 TLS는 단순 암호화 연결을 넘어 인증서 검증과 신뢰 CA를 사용한다.
- 파일 저장소의 동일 object key 중복 참조를 해소한 뒤 정리 작업을 실행한다.
  참조 수를 확인하지 않는 삭제 작업은 정상 파일을 함께 지울 수 있다.
- S3 백업을 내려받아 빈 데이터베이스에 복원하는 재해 복구 runbook과 정기 복구
  훈련을 추가한다.
- v26 컨테이너와 공유 인프라 컨테이너 모두에 로그 회전과 보존 상한을 둔다.
- 최근 자동 스냅샷과 배포 직전 수동 스냅샷의 존재를 확인한다.

## 5. 마이그레이션 정책: v26 baseline squash 완료

2026-08-14 v26의 15개 migration을 `0000_baseline.sql`로 squash했다. 운영 전용
백업을 먼저 생성하고 빈 임시 DB에서 52개 테이블과 삭제 대상 레거시 테이블 부재를
검증한 뒤, 운영 DB에서는 데이터 테이블을 건드리지 않고 Drizzle journal 기준점만
baseline 1건으로 전환했다. 기존 PHP 서비스와 원본 DB는 대상에서 제외했다.

모든 배포에서 다음을 자동 확인한다.

- 스키마 변경 후 생성해야 할 마이그레이션이 누락되지 않았는지
- baseline checksum과 snapshot/journal이 서로 일치하는지
- 빈 MySQL에 처음부터 끝까지 적용되는지
- bootstrap이 빈 DB와 재실행 모두에서 멱등적인지

## 6. 데이터베이스 정리와 인덱스 계획

### Phase A: 공개 전, 무손실 점검

- 선언 스키마와 실제 테이블·컬럼·FK 비교
- FK 고아 레코드, 중복 object key, 캐시 카운터 불일치 확인
- 인증코드 만료·학년도 결속 현황 확인
- 핵심 목록 쿼리의 `EXPLAIN` 결과와 slow query 기준선 저장
- 개인정보 보존 정책의 실제 삭제 대상 건수를 dry-run으로 확인

### Phase B: additive 변경

실제 쿼리 계획에서 이득이 확인된 경우에만 복합 인덱스를 추가한다. 우선 검토
대상은 다음 패턴이다.

- 공지: 공개 범위, 고정 여부, 게시일, 식별자
- 게시물: 게시판, 숨김·상태, 고정 여부, 작성일, 식별자
- 탐구활동서: 상태, 활동일, 식별자
- 상벌점: 학생, 기준일·생성일, 식별자

인덱스는 staging 데이터로 쓰기 비용과 사용 여부를 검증하고 추가한다. 컬럼 순서는
실제 필터와 정렬 조건을 기준으로 정하며, 추측으로 비슷한 인덱스를 중복 생성하지
않는다.

### Phase C: 사용처 전환

- `users`에 남은 학생 정보 미러 컬럼은 모든 읽기 경로가 정규화된 학생·재학
  테이블로 전환된 뒤 제거한다.
- 레거시 활동 기록, 미사용 반응 테이블, 인증 전환 컬럼은 코드·배치·리포트의
  참조가 0임을 확인하고 제거 후보로 표시한다.
- 본문 HTML과 에디터 JSON처럼 목적이 다른 이중 컬럼은 동기화 계약을 먼저
  문서화한다.

### Phase D: destructive 변경

삭제는 별도 승인, 직전 백업, 복원 검증, 관찰 기간을 거친 뒤 수행한다. 기존 PHP
원본 DB에는 적용하지 않는다.

## 7. 백업과 복구

공개 전 완료해야 할 최소 기준:

- DB 백업은 읽기 전용 전용 계정과 암호화 전송을 사용한다.
- 백업 객체는 비공개 저장소, 서버 측 암호화, 보존 정책, 무결성 해시를 사용한다.
- 배포 직전 v26 전용 DB 백업과 v26 인스턴스 스냅샷을 남긴다.
- 백업 생성 성공이 아니라 **격리된 빈 DB 복원 성공**을 복구 가능의 기준으로 삼는다.
- 복원 후 마이그레이션 상태, 핵심 테이블 건수, 읽기 전용 API smoke test를 확인한다.
- 최소 분기 1회 복구 훈련을 하고 복구 시간과 실패 원인을 기록한다.

백업 workflow가 외부에서 DB에 접근해야 한다면 광범위한 공인 접근을 열기보다
고정된 실행 경로 또는 서버 내부 실행을 사용한다. root 계정을 자동화에 사용하지
않는다.

## 8. 프론트엔드와 빌드

### 공개 전 확인

- web에는 canonical, description, Open Graph, Twitter card, favicon, sitemap과
  robots 정책을 둔다.
- admin과 인증 콜백 페이지는 검색 엔진 색인을 막는다.
- HTML은 재검증하고 해시가 붙은 정적 자산만 장기 immutable cache를 적용한다.
- 분석 도구에는 경로만 전달하고 query, hash, 인증코드, 사용자 식별정보를 보내지
  않는다.
- 개인정보처리방침의 분석 도구 설명과 실제 활성화 조건을 일치시킨다.

### 최적화 후보

대형 PNG·GIF는 시각 회귀 확인 후 표시 크기에 맞춘 WebP/AVIF로 변환한다. 원본은
소스 저장소 밖의 자산 보관 위치에 둔다. 번들 분석 결과 큰 라이브러리는 해당
페이지에서만 lazy load하며, 초기 화면에 필요하지 않은 관리자·엑셀 코드는 분리한다.

공개 전 데스크톱과 모바일에서 로그인, 비밀번호 재설정, 홈, 게시물 작성, 파일
업로드, 탐구활동서 신청의 5개 핵심 흐름을 브라우저 E2E로 검증한다.

## 9. 모니터링, 로그와 라이브러리

### 필요한 운영 신호

- API 5xx 수, 요청 지연, 컨테이너 재시작, 헬스체크 실패
- DB 연결 실패와 slow query
- Cognito, 이메일·문자, NEIS, YouTube, 객체 저장소 등 외부 연동 실패
- 디스크 사용량, Docker 이미지·볼륨·로그 증가량
- 백업·개인정보 보존 job의 성공과 실패

애플리케이션 로그에는 request ID를 넣되 비밀번호, 토큰, 인증코드, 쿠키, 이메일,
전화번호와 본문 개인정보를 기록하지 않는다. 구조화 로그와 중앙 오류 수집 도구는
도입 가치가 있다. 추천 순서는 다음과 같다.

1. `nestjs-pino` 등 구조화 로그와 request ID
2. Sentry 같은 오류 추적 도구(PII scrub 설정 필수)
3. Playwright 핵심 흐름 E2E
4. 빌드 분석기는 개발 의존성으로만 추가

상태 관리, SSR, PWA, 별도 메시지 브로커는 현재 요구만으로 추가하지 않는다.
운영 복잡성을 늘리는 라이브러리는 측정된 문제와 담당 운영자가 있을 때만 채택한다.

## 10. 공유 인프라 제약

v26 서버에는 프록시와 다른 서비스가 함께 존재할 수 있으므로 다음 원칙을 지킨다.

- v26 배포 경로, Compose project name, 볼륨, 네트워크 이름을 명시적으로 분리한다.
- `docker compose down`, prune, 전역 nginx reload 같은 명령을 공용 범위에서 실행하지
  않는다.
- 프록시·DNS·TLS 설정 변경은 호스트 단위 영향을 먼저 확인한다. zone 전체 설정은
  기존 서비스에 영향을 줄 수 있으므로 v26 공개 작업에 포함하지 않는다.
- 데이터베이스, 프록시 관리 UI, 캐시, 내부 제어 API는 인터넷 전체에 노출하지
  않는다. 기존 노출을 정리할 때도 기존 서비스 소유자와 별도 작업 창을 잡는다.
- TLS 강화는 최종 목표지만 공유 도메인의 최소 TLS나 모드를 한 번에 바꾸지 않는다.
  먼저 v26 전용 호스트에서 검증하고 서비스별로 전환한다.

서버 폴더는 서비스별로 `deploy`, `data`, `backup`, `logs` 책임을 분리한다. 이름만
보고 미사용으로 판단해 삭제하지 않고, 실행 중 컨테이너·systemd·cron·프록시 참조를
확인한 뒤 삭제 후보 목록과 보존 기한을 만든다.

## 11. 공개 절차

### A. 변경 동결

- [ ] 공개 후보 커밋을 지정하고 기능 변경을 동결한다.
- [ ] branch protection과 필수 CI를 적용한다.
- [ ] secret scan, production dependency audit, lint, typecheck, test, build를 통과한다.
- [ ] 이미지 digest와 배포 대상 커밋을 기록한다.

### B. 데이터와 복구 준비

- [ ] v26 DB 백업을 생성하고 격리 복원을 검증한다.
- [ ] v26 인스턴스 스냅샷을 생성한다.
- [ ] 인증코드를 만료 정책이 있는 코드로 재발급한다.
- [ ] legacy seed와 테스트 데이터 공개 범위를 승인한다.
- [ ] 롤백 담당자와 판단 기준을 정한다.

### C. staging 검증

- [ ] 학생·교직원·관리자 최소 권한 계정으로 로그인한다.
- [ ] 비밀번호 재설정, 세션 공유, 로그아웃을 확인한다.
- [ ] 공지·게시판·댓글·첨부·신고·좋아요를 확인한다.
- [ ] 상벌점 조회·부여 권한과 알림을 확인한다.
- [ ] 탐구활동서 신청·승인·반려·출력을 확인한다.
- [ ] 외부 연동 실패 시 사용자 오류와 운영 로그가 적절한지 확인한다.
- [ ] 개인정보·토큰이 URL, 분석 도구, 로그에 남지 않는지 확인한다.

### D. 제한 공개

- [ ] 소수의 교직원·학생 계정으로 먼저 공개한다.
- [ ] 24~72시간 동안 오류율, 지연, 디스크, DB 연결, 외부 연동을 관찰한다.
- [ ] 인증코드는 승인된 전달 경로로만 배부한다.
- [ ] 문제가 없을 때만 전체 학생에게 URL을 공개한다.

### E. 승격

기존 도메인 승격은 별도 프로젝트다. v26 안정화만으로 자동 진행하지 않는다.
승격 전 기존 서비스의 URL, 쿠키 범위, 인증 콜백, 캐시, SEO canonical, 링크와
롤백 DNS TTL을 별도로 검토한다.

## 12. 롤백 기준과 절차

다음 중 하나면 즉시 신규 인증코드 배부를 중단하고 롤백한다.

- 로그인·권한 오류로 다른 사용자의 정보가 보임
- 데이터 손실·중복 쓰기·첨부파일 오접근
- 5xx 또는 외부 연동 실패가 사전 기준을 지속 초과
- DB 연결 고갈, 디스크 급증, 반복 재시작

롤백 순서:

1. v26 신규 트래픽과 계정 배부를 중단한다.
2. 직전 정상 이미지 digest로 v26 컨테이너만 되돌린다.
3. DB가 변경되었다면 운영 DB에 즉시 역마이그레이션하지 않는다. 격리 복원본으로
   영향과 복구 방법을 확인한다.
4. 필요할 때만 승인된 v26 백업을 복원한다.
5. 기존 서비스는 계속 유지하며 재시작·설정 변경하지 않는다.
6. 원인, 영향 범위, 재발 방지 조치를 기록한 뒤 재공개한다.
